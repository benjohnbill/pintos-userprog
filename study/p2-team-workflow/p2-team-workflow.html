8팀 조진근입니다. 저희 팀의 일주일을 날짜순으로 보여 드리겠습니다. 한 줄로 요약하면, 누가 짠 코드든 합칠 수 있게 — 컨벤션, 테스트 명령, 분업표였습니다.

목 · 10.15

목요일(10/15) :  협업 원칙과 컨벤션 정립

CONVENTION.md · PR #104목

지난주 발표가 끝나고 코치님께서 팀 컨벤션을 미리 정하고 가라고 하셨죠.

▸1그래서 첫날 칠판부터 그렸습니다. 팀 활동은 회의와 PR 단위로 돌고, 그 단위는 작업이 정합니다. 그래서 작업을 공통과 분할로 나눴습니다.

▸2둘은 고정이 아닙니다. 시간이 부족하면 AI로 시스템 콜 단위로 일을 나눠 분할로 가고, 로직과 변수를 많이 공유하면 다 짜 보고 리뷰하는 공통으로 돌아옵니다.

▸3이번 주 핵심인 fork, wait, exec는 공통으로 잡았고, 그 선행 요건에서 첫날 할 일이 나왔습니다. 분할은 프로세스 syscall이 끝난 뒤로 미뤘습니다.

▸4다른 한 축은 컨벤션입니다. 오픈소스 규약을 포매터와 린터로 묶었고, 여기서 CONVENTION.md와 같은 테스트 명령 make ptest가 나왔습니다. 이 지도가 어떻게 이루어졌는지 차례로 보여 드리겠습니다.

github.com/benjohnbill/pintos-userprog · PR #104 – #118목 – 수

저희 팀 저장소의 일주일을 git graph 하나로 그렸습니다. 가운데가 develop이고, 셋 다 같은 main에서 출발해서 각자 브랜치에서 짰습니다.

맨 아래 줄은 합칠 때마다 잰 테스트 통과 수입니다.

▸1토요일까지 셋이 각자 args와 write, exit을 짰습니다.

▸2토요일 밤 첫 merge에서는 AI에게 컨벤션 충실도, 안정성, 복잡도, 가독성으로 평가하게 해서 골랐습니다. args는 승영님 것, write와 exit은 누리님 것이 들어갔습니다.

▸3월요일에는 테스트 도구를 먼저 넣고, fork, wait, exec는 셋이 각자 짰습니다.

▸4월요일 merge는 기준이 달랐습니다. 저녁 9시까지 동작하는 것, 그리고 서로 맞물리는 것이었습니다. wait와 fork는 nuri님 것, exec는 승영님 것이 들어갔고, 제 wait와 exec는 빠졌습니다.

▸5합칠 때마다 각자 develop을 받아가서 그 위에서 다음 작업을 시작했습니다.

▸6수요일에는 integrate 없이 기능마다 develop으로 바로 PR을 올렸고, 저녁에 96개를 모두 통과해 main으로 합쳤습니다. 이 숫자는 전부 같은 명령 하나, make ptest로 쟀습니다.

▸7그리고 이 빨간 가지가 제가 혼자 판 빈칸 다시 짜기 브랜치입니다. 마지막에 다시 말씀드리겠습니다.

팀 전용 테스트 도구: make ptest: 
테스트 결과는 분업표로 자동 반영.

각자 자기 브랜치에서
benjohnbillbenjohnbill→ make ptest → 내 블록 체크 Nurinuri→ make ptest → 내 블록 체크 승영JSY-*→ make ptest → 내 블록 체크
분업표 한 장을 셋이 같이 본다 → 누가 어디까지 됐는지 회의 없이 보인다
회색 = 여러 사람 코드가 함께 필요한 테스트
icount
QEMU가 실제 시간 대신 명령 수로 시간을 센다. 여러 개를 동시에 돌려도 결과가 흔들리지 않는다.
SHIFT
명령 하나 = 2SHIFT ns. 3–8로 바꿔 돌리며 경쟁 상태를 찾는다.
JOBS
코어 수만큼 QEMU를 동시에 띄운다 (-j$(nproc)).
TIMEOUT
테스트 하나의 제한 시간. 기본 5초, 느린 노트북은 10초.
Makefile · scripts/plan-check.py · team-plan.html토 – 월

▸1테스트를 계속 돌려야 하니 도구를 만들었습니다. 이게 실제로 쓰던 분업표 페이지입니다. 이제 수요일 코드로 make ptest를 한 번 돌렸을 때 이 페이지가 채워지는 모습을 재현해 보겠습니다. 칸 색은 그 테스트를 통과시킨 코드를 누가 짰는지입니다.

▸2평소에는 각자 자기 브랜치에서 make ptest를 돌리고, 결과가 자기 블록에 체크됩니다. 그래서 회의 없이도 누가 어디까지 됐는지 셋이 같은 화면으로 봤습니다.

▸3속도는 QEMU의 icount 모드와 코어 수만큼의 병렬 실행에서 나옵니다. SHIFT를 바꿔 돌리면 타이밍이 달라져서 경쟁 상태도 점검할 수 있습니다.

Convention · CONVENTION.md

A : 자동저장 | B : 수동 체크 | C : 직접 체크

CONVENTION.md · .clang-format · .clang-tidy · PR #110목 – 수

CONVENTION.md는 세 구역으로 나뉩니다. 오른쪽으로 갈수록 도구가 해 주는 몫이 줄어듭니다.

▸1A는 모양입니다. 들여쓰기, 중괄호, 공백은 저장하는 순간 clang-format이 고칩니다. make format은 이걸 파일 전체에 적용합니다.

▸2B는 이름입니다. snake_case와 대문자 상수는 clang-tidy가 에디터에 밑줄로 알려 주고, make lint는 A와 B를 함께 검사합니다.

▸3C는 이름 짓는 규칙입니다. 이건 도구가 못 잡아서 사람끼리 합의했고, merge할 때는 AI가 이 규칙으로 판단했습니다. 화요일 merge에서 file_descriptor가 fd_entry로, process_get_file이 process_find_file로 바뀐 게 그 예입니다.
